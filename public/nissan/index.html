The approach

Good / Better / Best

Senior management and maintenance leadership do not need to approve a giant replacement program. The choice is how much change to take on now, what capability to unlock next, and where CESMII i3X anchors the data strategy.

Good

Stabilize and simplify

Best when: leadership wants faster improvement without major architecture change.

  • Keep current Proficy / CIMPLICITY stack.
  • Centralize access through one dashboard.
  • Improve structured fault entry and reason coding.
  • Use SQL where it already works.
Better

Build the missing middle

Best when: Nissan wants the strongest practical answer for maintenance performance and data quality.

  • Add historian for OT time-series and alarm/event data.
  • Add an i3X-aligned context / UNS layer.
  • Use one maintenance cockpit for faults, RCA, parts, and escalation.
  • Publish curated operational context to cloud analytics.
Best

Standardize for scale

Best when: leadership wants an interoperable long-term operating layer that supports AI and fleet learning.

  • Combine historian + i3X UNS layer + modern frontline UI.
  • Use CESMII SM Profiles + i3X as the interoperability contract.
  • Feed a cloud data platform with clean contextualized events.
  • Scale the operating model across body, paint, and assembly.
Brooksource recommendation

Recommended path: Better now, designed to become Best

The sweet spot is to make the Better option the primary recommendation, but architect it so Nissan does not have to backtrack later to reach Best.

Why Better is the strongest management answer

  • It improves maintenance performance in a visible way without destabilizing the current control stack.
  • It fixes the most important gap: the missing context layer between plant systems and enterprise analytics.
  • It gives Nissan a real operating experience — one cockpit, one event record, one escalation pathway.
  • It creates the conditions for AI to be useful later instead of speculative now.

How CESMII i3X fits each option

  • Good: a reference point for where data and events should eventually land.
  • Better: the design center for asset identity, event identity, and reusable plant context.
  • Best: the plant-wide interoperability spine that keeps the architecture portable and future-proof.

Interoperability spine

Why CESMII SM Profiles + i3X should sit at the center

This is the cleanest way to explain data management and interoperability: use SM Profiles as the common language for data-in-context, and i3X as the open interaction model for how systems share it.

Asset identity

Every line, station, robot, vision unit, and utility asset gets one durable, human-readable identity.

Event identity

Faults, alarms, downtime events, and predictive warnings are captured once and reused everywhere.

i3X

SM Profiles + i3X

The centerpoint for Nissan's plant data management: common semantics, portable context, and open interoperability between existing systems, future apps, and enterprise analytics.

Transport vs. meaning: a UNS / MQTT broker moves data — pub/sub, discoverable, hub-and-spoke instead of point-to-point. SM Profiles + i3X give that data meaning and governance: one asset and event model, with ownership and lineage built in. They are complementary — the broker carries what the model defines, so a Unified Namespace and this model reinforce each other rather than compete.

Action identity

Responses use common codes, evidence, and close-out logic so the plant learns from every intervention.

Cloud portability

Contextualized manufacturing events flow cleanly into whatever cloud data platform Nissan chooses instead of being trapped in local islands.

Nissan-friendly translation: if it happens on the plant floor, it should have one name, one place to land, one history, and one way to escalate.
Fit with the bigger picture

How this complements Nissan's enterprise data direction

This is not a competing island. It is the execution beachhead for Nissan's plant-to-enterprise data direction — the same open asset and event model, proven running on one area before it scales across the plant and the fleet.

Same destination

One open asset and event model, governed data flowing cleanly to whatever enterprise analytics platform Nissan chooses — the direction plant-to-enterprise data is already heading.

Why it matters: no conflict with the broader data strategy.

Proven before it scales

One area, running, de-risks the plant-wide and Americas-wide rollout. The hardest part of any data program is holding the model together as it grows — this proves it can, on real equipment, before the big commitment.

Why it matters: the model holds as new areas and assets come online.

Reuses what's owned

CIMPLICITY, Kepware, and FAULT stay. The value is the missing middle — context and one event record — not a rip-and-replace backbone.

Why it matters: lower risk, faster to proof.
Grounded in best practice

Patterns this recommendation borrows from

The objective is not novelty. It is to borrow the strongest operating patterns from world-class plants and remote operations environments, then translate them for Nissan Smyrna.

Remote operations center logic

Central watch desk, fleet-style visibility, standard playbooks, and shared escalation are what make complex assets manageable at speed.

Why it matters: it changes the feel from dashboarding to real operations.

Historian-first OT storage

High-speed time-series and alarm/event data belong in infrastructure built for OT retrieval, compression, and trending.

Why it matters: better bad-actor analysis and AI features.

Connected-worker guidance

Best-in-class plants embed SOPs, issue capture, and tacit knowledge directly into the front-line workflow.

Why it matters: faster troubleshooting and less re-keying.

Open interoperability

Plants that normalize context before pushing data upward make future tool choices easier and reduce integration regret.

Why it matters: Nissan keeps optionality.

Engagement arc

How we get to the target state — a five-phase assessment

Before the day-in-the-life is real, there is a disciplined path to it. This is the assessment arc: evaluate the current state, benchmark the gaps, and deliver a prioritized modernization roadmap — structured so every recommendation traces to observed evidence, not assumption.

1

Pre-Assessment Planning

Kickoff and team alignment, baseline documentation, a stakeholder questionnaire, and scoping of the focus area.

Goal: team buy-in, project plan, baseline inputs gathered.
2

Onsite Assessment

Onsite evaluation of the centralized control room and target area; document processes, workflows, and pain points with the site teams.

Goal: validated current-state documentation.
3

Gap Analysis & Benchmarking

Compare practices against maintenance & reliability and manufacturing industry benchmarks; identify gaps and prioritized, actionable recommendations.

Goal: gap analysis + benchmarking summary.
4

Integrated Controls Modernization Roadmap

Define investment priorities and an ROI tracking framework tied to uptime, MTTR, and maintenance cost; outline training and adoption.

Goal: prioritized modernization roadmap.
5

Executive Presentation

Translate technical findings into business outcomes — reliability impact and cost avoidance — in an executive-ready package.

Goal: decision-ready findings + roadmap.
Why it is sequenced this way: current state → benchmarked gaps → prioritized roadmap → executive decision. Each phase's output is the next phase's input, so the final roadmap is grounded in observed evidence rather than assumption.
